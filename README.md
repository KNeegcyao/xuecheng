## 介绍一下项目？

​		面试官您好，我以这张图为您介绍一下我们实验室的**在线教育平台的核心业务流——课程编辑与发布**。它的核心目标是让教学机构能创建一门课程，并经过运营审核后最终发布给用户。

**1.教学机构**

> 首先是**教学机构**侧，这是课程的源头。老师在这里进行‘添砖加瓦’式的操作：

- **写入核心信息**：包括课程基础信息、营销信息、课程计划（章节）、师资信息等。这些操作都调用**内容管理服务**，数据直接落盘MySQL。
- **处理多媒体内容**：当老师上传图片和视频时，请求会到达**内容管理服务**。
  - 对于图片，我们使用**MinIO**进行存储，并将存储信息回写到数据库。
  - 对于视频，因为处理耗时，我们采用了**异步化**策略。服务会先将视频文件存入MinIO，然后向数据库插入一条`待处理`的视频记录，同时向RabbitMQ发送一条**视频处理消息**。这样就快速响应了老师，告诉他上传成功，后台会继续处理。

2.**运营人员**

>课程提交后，就进入**运营人员**的审核环节。运营人员会复查机构提交的所有信息，进行‘质检’。

- 运营端的操作和机构端类似，也是调用**内容管理服务**的接口，但其核心职责是**审核与确认**。
- 当运营点击‘课程发布’时，这就是整个流程的**触发器**。这一步不会直接完成所有事，而是会向数据库写入一条**课程发布消息**（这里我们用了本地事务表保证一致性），标志着这门课程进入了发布流程。

**3.内容管理模块**

> 接下来，系统的‘异步任务中枢’——**数据管理服务**开始工作

- 它内部有一个**定时任务**（比如用XXL-JOB调度），会周期性地扫描那条‘课程发布消息’。
- 一旦扫描到新任务，它就会执行一系列发布动作：
  1. **缓存课程信息**：从数据库查询完整的课程信息，存入**Redis**。这样用户访问时可以直接读缓存，性能极高。
  2. **发送消息**：向消息队列（如RabbitMQ）发送一个**课程发布事件**。这么做是为了**解耦**，通知搜索服务等其他子系统：‘喂，有一门新课程上线了！’。

**4.搜索服务**

> 最后，由**搜索服务**来收尾，保证用户能搜到这门课。

- 它监听了数据管理服务发出的**课程发布事件**。
- 收到消息后，它会从数据库或缓存中获取最新的课程数据，然后通过**Elasticsearch**的API将课程信息构建到索引中。
- 至此，一门课程就完全上线了，用户可以在前台搜索和购买。

# **页面静态化**：使用FreeMarker对页面静态化生成HTML页面上传至文件系统，提供高效的发布过程。

### 为什么要使用FreeMarker页面静态化？

​     FreeMarker是一款模板引擎，即一种基于模板和要改变的数据， 并用来生成输出文本(HTML网页，电子邮件，配置文件，源代码等)的通用工具。

<img src="https://cdn.jsdelivr.net/gh/KNeegcyao/picdemo/img/image-20250813100752131.png" alt="image-20250813100752131" style="zoom:50%;" />

像课程详情页、新闻详情页这类**内容相对固定、访问量高**的页面，用模板引擎生成**静态 HTML 文件**更高效。比如项目中的课程预览静态化，生成 HTML 后可直接部署到 MinIO，用户访问时无需实时渲染，**加载更快、服务器压力更小**。

用模板引擎可在后端直接控制渲染结果，**减少前端判断逻辑**（比如课程价格是否显示、内容是否隐藏）。

3. **成本效益**：开源免费，用实验室服务器搭建集群，避免云存储费用，符合学生项目预算；
4. **运维友好**：单二进制文件部署，降低学习成本，快速满足项目上线需求。”

### 如何设计课程视频的分块存储逻辑？分块大小如何确定？

小文件（如图片、作业）分块为 1MB~2MB，大文件（如视频）分块为 5MB~10MB，以减少分片数量并提高合并效率。

5MB 分块可平衡传输效率与网络波动容忍度。

**分块上传流程**

1、前端对文件进行分块。

2、前端上传分块文件前请求媒资服务检查文件是否存在，如果已经存在则不再上传。

3、如果分块文件不存在则前端开始上传

4、前端请求媒资服务上传分块。

5、媒资服务将分块上传至MinIO。

6、前端将分块上传完毕请求媒资服务合并分块。

7、媒资服务判断分块上传完成则请求MinIO合并文件。

8、合并完成校验合并后的文件是否完整，如果完整则上传完成，否则删除文件。



1. 客户端将文件切分为多个分块（如 5MB/块）。
2. 使用 MinIO Java SDK 的 `UploadPart` 接口并行上传分块（多线程处理）。
3. 所有分块上传完成后，调用 `CompleteMultipartUpload` 合并为完整文件。

### **断点续传怎么实现？**

1. **检查文件是否存在 (checkFile)**

   \- 前端：上传文件前，前端计算整个文件的MD5值（文件唯一标识），调用`checkFile`接口。

   \- 后端：根据MD5值查询数据库（`mediaFiles`表）和MinIO存储，如果文件存在，则直接返回“文件已存在”（秒传），否则进入下一步。

2. **检查分块是否存在 (checkChunk)**

   \- 前端：将大文件切割成多个分块（例如每个分块5MB），然后对每个分块，按序号（0,1,2,...）调用`checkChunk`接口检查该分块是否已上传。

   \- 后端：根据文件MD5和分块序号，生成分块路径（如`a/b/fileMd5/chunk/0`），然后检查MinIO中是否存在该分块。如果存在则跳过该分块上传，不存在则记录需要上传的分块。

3. **上传分块 (uploadChunk)**

   \- 前端：对需要上传的分块，逐个调用`uploadChunk`接口，将分块文件（二进制数据）上传。

   \- 后端：

​        a. 生成分块存储路径（与检查分块时路径一致）。

​        b. 将分块文件上传到MinIO的指定路径。

​        c. 返回上传结果（成功或失败）。

4. **合并分块 (mergechunks)**

   \- 前端：所有分块上传完成后，调用`mergechunks`接口，传入文件MD5、总分块数、文件名等信息。

   \- 后端：

​        a. 根据文件MD5，获取所有分块的路径（分块路径规则：`fileMd5[0:1]/fileMd5[1:2]/fileMd5/chunk/0,1,2,...`）。

​        b. 调用MinIO的`composeObject`方法，将所有分块合并成一个文件，存储在合并后的路径（如`a/b/fileMd5/fileMd5.ext`）。

​        c. 合并完成后，从MinIO下载合并后的文件，计算其MD5值，与前端传入的MD5（文件唯一标识）进行对比，确保文件完整性。

​        d. 校验通过后，将文件信息（如文件名、大小、存储路径等）存入数据库（`mediaFiles`表）。

​        e. 清理分块文件：调用MinIO的批量删除接口，删除该文件对应的所有分块。

​        f. 返回合并结果（成功或失败）。

 关键点：

\- **断点续传**：在分块上传过程中，如果中断，下次可以重新检查分块，只上传缺失的分块。

\- **秒传**：在第一步检查文件时，如果发现文件已存在，则直接跳过上传，实现秒传。

\- **文件完整性校验**：合并后重新计算MD5，确保文件上传过程中没有损坏。

\- **分块清理**：合并后自动删除分块，避免占用存储空间。

# 课程发布任务调度：基于 XXL-JOB 搭建任务调度中心，统一调度5类定时任务；配置失败重试机制，支持可视化任务监控与调度配置。

### 为什么要使用分布式任务调度XXL-JOB?

像     每隔24小时执行数据备份任务。

​       12306网站会根据车次不同，设置几个时间点分批次放票。

​        某财务系统需要在每天上午10点前结算前一天的账单数据，统计汇总。

​        商品成功发货后，需要向客户发送短信提醒。

这些场景， Timer 和 ScheduledExecutor 都仅能提供基于开始时间与重复间隔的任务调度，不能胜任更加复杂的调度需求。

---

### **失败重试机制如何实现？**

“双保险机制：

1. **框架级重试**：XXL-JOB自带重试参数（如失败自动重试2次）
2. **业务级重试**：代码内嵌try-catch循环（应对数据级异常）”

```java
@XxlJob("courseExpireJob")
public void expireJob() {
    // 手动重试（需捕获异常）
    for (int i = 0; i < 3; i++) { // 最大重试3次
        try {
            courseService.checkExpire();
            break; // 成功则退出
        } catch (Exception e) {
            if (i == 2) sendAlert(e); // 最终失败发告警
        }
    }
}
```

### 分布式任务调度的好处？

1、并行任务调度

​    并行任务调度实现靠多线程，如果有大量任务需要调度，此时光靠多线程就会有瓶颈了，因为一台计算机CPU的处理能力是有限的。

​    如果将任务调度程序分布式部署，每个结点还可以部署为集群，这样就可以让多台计算机共同去完成任务调度，我们可以将任务分割为若干个分片，由不同的实例并行执行，来提高任务调度的处理效率。

2、高可用

​        若某一个实例宕机，不影响其他实例来执行任务。

3、弹性扩容

​        当集群中增加实例就可以提高并执行任务的处理效率。

4、任务管理与监测

​        对系统中存在的所有定时任务进行统一的管理及监测。让开发人员及运维人员能够时刻了解任务执行情况，从而做出快速的应急处理响应。

5、避免任务重复执行

​        当任务调度以集群方式部署，同一个任务调度可能会执行多次，比如在上面提到的电商系统中到点发优惠券的例子，就会发放多次优惠券，对公司造成很多损失，所以我们需要控制相同的任务在多个运行实例上只执行一次。

### 如何进行分布式任务处理呢？

我们会启动多个执行器组成一个集群，去执行任务

分片广播策略，分片是指是调度中心以执行器为维度进行分片，将集群中的执行器标上序号：0，1，2，3...，广播是指每次调度会向集群中的所有执行器发送任务调度，请求中携带分片参数。

每个执行器收到调度请求同时接收分片参数。

xxl-job支持动态扩容执行器集群从而动态增加分片数量，当有任务量增加可以部署更多的执行器到集群中，调度中心会动态修改分片的数量。广播分片方式不仅可以充分发挥每个执行器的能力，并且根据分片参数可以控制任务是否执行，最终灵活控制了执行器集群分布式处理任务。

### 如何保证多个执行器不会查询到重复的任务呢？

### 如何保证任务不重复执行？XXL-Job 怎么解决任务重叠、分布式调度的核心逻辑

通过作业分片方案保证了执行器之间查询到不重复的任务，如果一个执行器在处理一个视频还没有完成，此时调度中心又一次请求调度，为了不重复处理同一个视频该怎么办？

**首先配置调度过期策略：**

- **调度过期策略**：调度中心错过调度时间的补偿处理策略，包括：忽略、立即补偿触发一次等；     

- **忽略**：调度过期后，忽略过期的任务，从当前时间开始重新计算下次触发时间；        

  - **立即执行一次**：调度过期后，立即执行一次，并从当前时间开始重新计算下次触发时间； 
    -  **阻塞处理策略**：调度过于密集执行器来不及处理时的处理策略；

这里我们选择**忽略**，如果立即执行一次就可能重复执行相同的任务。

**再看阻塞处理策略：**

阻塞处理策略就是当前执行器正在执行任务还没有结束时调度中心进行任务调度，此时该如何处理。

- **单机串行（默认）**：调度请求进入单机执行器后，调度请求进入FIFO队列并以串行方式运行；        
- **丢弃后续调度**：调度请求进入单机执行器后，发现执行器存在运行的调度任务，本次请求将会被丢弃并标记为失败；       
- **覆盖之前调度**：调度请求进入单机执行器后，发现执行器存在运行的调度任务，将会终止运行中的调度任务并清空队列，然后运行本地调度任务；

这里如果选择覆盖之前调度则可能重复执行任务，这里选择 **丢弃后续调度**或**单机串行方式**来避免任务重复执行。因为课程提醒是低频任务，串行执行能保证逻辑严谨，避免重复发提醒



**分布式调度的核心机制**：“调度中心通过「心跳检测」感知执行器的在线状态，再用「路由策略」（如轮询、故障转移）把任务分配给合适的执行器。执行器完成任务后，会把日志、状态回传给调度中心，这样我们在 Admin 平台就能实时看到任务是否成功、耗时多久。



*这些还做不到任务不会重复执行，还需要保证任务处理的幂等性。*

解决幂等性常用的方案：

1）数据库约束，比如：唯一索引，主键。

2）乐观锁，常用于数据库，更新数据时根据乐观锁状态去更新。

3）唯一序列号，操作传递一个唯一序列号，操作时判断与该序列号相等则执行。

基于以上分析，在执行器接收调度请求去执行视频处理任务时要实现视频处理的幂等性，要有办法去判断该视频是否处理完成，如果正在处理中或处理完则不再处理。这里我们在数据库视频处理表中**添加处理状态字段**，视频处理完成更新状态为完成，执行视频处理前判断状态是否完成，如果完成则不再处理。

### 说一下这个视频上传与处理流程？

![image-20250813141614673](https://cdn.jsdelivr.net/gh/KNeegcyao/picdemo/img/image-20250813141614673.png)

**1. 上传阶段**：用户通过客户端上传视频文件，请求首先进入网关进行路由和初步校验，随后分发到媒资服务。
 **2. 分块与合并**：媒资服务会将大文件切分成多个小分片（例如5MB/块），并逐个上传到MinIO。上传过程中会记录每个分片的状态（如已上传的分片序号），当所有分片上传完成后，媒资服务会将这些分片合并成完整的视频文件。
 **3. 存储管理**：合并后的视频文件通过网关上传至MinIO服务器，MinIO作为分布式对象存储，支持高可用和海量文件存储。
 **4. 任务调度**：视频处理任务由XXL-JOB任务调度中心统一管理，根据规则（如视频ID与分片数取模）分配任务。
 **5. 处理执行**：文件处理服务根据调度指令，调用FFmpeg等工具对视频进行转码、截图等操作，并将处理结果（如封面路径、转码后的视频链接）记录到数据库。
 **6. 数据持久化**：整个流程中的关键信息（如分片状态、处理结果）都会存入数据库，确保数据可追溯。

**补充亮点**：

- **断点续传**：通过分片上传和Redis记录已上传分片，支持网络中断后继续上传。
- **高并发优化**：分片并发上传、XXL-JOB分布式调度，提升处理效率。
- **可靠性保障**：MinIO分布式存储+数据库双备份，避免数据丢失(任务完成记录写入历史表)

1. **文件上传与存储**
   - 用户上传视频时，**媒资服务**将大文件切分为分片（如5MB/块），逐个上传至 **MinIO** 分布式存储。
   - 每个分片上传完成后，服务会记录分块信息（如 `fileMd5`、`bucket`、`objectName`），并最终合并生成完整视频文件。
   - 合并后，文件路径（`url`）和元数据（如 `companyId`、`auditStatus`）会持久化到 **数据库** 的 `MediaFiles` 表中。
2. **任务调度与处理**
   - **任务分片策略**：通过 `shardTotal` 和 `shardIndex` 参数将任务均匀分配到多个实例（如 `XXL-JOB` 调度器），避免单点压力。
   - **待处理任务表**：若文件类型为视频（如 `.avi`），会将其插入 `MediaProcess` 表，标记为待处理（`status=1`）。
   - **任务锁定**：通过 SQL 更新语句（`update media_process set status='4' where id=#{id}`）独占任务，防止多实例重复处理。
3. **处理结果与状态更新**
   - **处理成功**：更新 `MediaFiles.url` 为处理后的文件路径，并将任务移动到历史表 `MediaProcessHistory`。
   - **处理失败**：记录错误信息（`errorMsg`），并增加失败计数（`failCount`），若重试超过阈值则标记为失败。
   - **事务保障**：通过 `@Transactional` 注解确保数据库操作的原子性，避免数据不一致。

1、在数据库中有一张文件表记录minio中存储的文件信息。

### 遇到的难处？

***一.问题：进行视频处理任务调度时，频繁读写 `MediaProcess` 表（获取任务、更新状态、删除记录）可能导致数据库性能瓶颈，数据库压力过大。***

**优化方案：**

- 引入消息队列（MQ）：

  将待处理任务从数据库迁移到 MQ，通过消息驱动处理流程。

  - **示例**：视频上传完成后发送 `ProcessVideo` 消息到 MQ，消费者拉取任务处理。

- 优点：

  - 降低数据库压力，避免分片查询和事务锁争用。
  - 提升系统扩展性，支持横向扩展消费者实例。

[视频上传] -> [发送 MQ 消息] -> [MQ 消费者拉取任务] -> [处理视频] -> [更新 MinIO + 发送结果通知]

1. **任务入队**：
   - 视频上传完成后，发送 `ProcessVideo` 消息到 MQ。
   - 消息体包含 `fileId`、`bucket`、`filePath` 等必要信息。
2. **任务消费**：
   - 消费者监听 MQ，拉取任务后执行转码逻辑（与当前代码逻辑类似）。
   - 消费成功后发送 `ProcessCompleted` 消息通知下游服务更新状态。
3. **状态持久化**：
   - 处理结果通过 MQ 传递，避免直接更新数据库（可选：最终一致性）。
   - 仍需记录关键元数据（如 `MediaFiles.url`）到数据库，但可异步更新。

***二.问题：如果有线程抢占了某个视频的处理任务，如果线程处理过程中挂掉了，该视频的状态将会一直是处理中，其它线程将无法处理，这个问题需要用补偿机制。***

**解决方法：**

 **RabbitMQ 的 TTL + 死信队列 + 数据库条件更新**

1. **任务启动**：

   - 用户上传视频后，任务状态变为 `processing`。
   - 向队列 A 发送消息，30 分钟后触发超时检测。

2. **任务正常完成**：

   - 转码服务在 25 分钟内完成任务，状态变为 `success`。
   - 当消息在 30 分钟后过期成为死信时，死信消费者会检查数据库状态。由于状态已变更，消费者会忽略该消息。

3. **任务超时**：

   - 如果处理线程挂掉，任务无法完成，消息会在 30 分钟后过期，自动进入死信队列。
   - 死信消费者接收到消息后，查询数据库状态。如果状态仍为 `processing`，则执行条件更新（例如 `UPDATE videos SET status = 'failed' WHERE id = ? AND status = 'processing'`），将状态改为 `failed`。这样，系统可以重新调度或允许用户重试。

   这个方案确保了即使线程挂掉，任务状态也能自动恢复，避免了手动干预。关键点在于利用了 RabbitMQ 的死信机制和数据库的条件更新，实现了幂等性（避免重复更新）和可靠性。

   

   **在设计过程中，我们也评估了其他几种方案：**

   - **定时任务扫描**：使用 调度器定期扫描数据库中的 `processing` 状态任务，检查超时并更新状态。但这种方法会增加数据库压力（尤其是大量任务时），而且扫描间隔设置需要权衡：间隔太短影响性能，间隔太长则实时性差。此外，它引入了额外的调度组件，增加了系统复杂度。
   - **分布式锁**：使用 Redis 或 ZooKeeper 为每个任务设置分布式锁，线程挂掉后锁会自动超时释放。但这种方法需要维护锁的生命周期，并且可能遇到锁竞争或锁失效问题，实现起来较复杂，且无法直接处理状态恢复。

   **我们选择 RabbitMQ TTL + 死信队列方案的主要原因包括：**

   1. **可靠性和成熟度**：RabbitMQ 提供了消息持久化、死信机制和可靠投递，确保消息不丢失，补偿逻辑稳定运行。
   2. **解耦和异步**：将处理逻辑和补偿逻辑分离，通过消息队列异步处理，降低了系统耦合度，提高了可扩展性。
   3. **性能优化**：避免了频繁的数据库查询（如定时扫描），减少了数据库压力，尤其适合高并发场景。
   4. **简洁性和维护性**：利用现有的消息队列基础设施，无需引入额外组件（如调度器），代码实现相对简单，易于维护和监控。
   5. **幂等性保障**：通过数据库条件更新，确保补偿操作只执行一次，即使消息重复也能正确处理。

   

   **为什么设置是30min呢？**

   我们小组上传视频，发现大部分都在25min之内能上传完，考虑到网络等问题我们就+5min作为一个缓冲时间，而且30min可以作为一个让用户能接受的结果等待时间，如果时间太长，用户任务真正早就失败了，还需要等这么长时间。

   **如果有的视频超过30min怎么办？为什么不用动态TTL？**

   对极少数的我们考虑过动态设置不同的TTL值，比如根据视频大小计算时间，但对于我们来说实现过于复杂，所以我们还是选择统一的，覆盖绝大多数场景的值。

# 分布式锁优化:对课程过期提醒等高并发任务，基于 Redisson 实现 Redis 分布式锁，替代数据库乐观锁方案，解决多实例任务调度时的资源竞争问题，显著降低任务重复执行率，提升系统可靠性?

## 讲一讲这一部分，为什么要用redisson分布式锁代替数据库乐观锁？

当时我们的 “课程过期提醒” 是个**高并发定时任务**—— 多个服务实例会同时触发调度，去扫描待提醒的课程。如果不做控制，就会出现 **“多实例重复执行同一段逻辑”** 的问题：比如多个实例都给同一批用户发了提醒，既造成资源浪费，又给用户带来骚扰，还可能引发数据库写冲突。

最开始我们想过用**数据库乐观锁**（比如给任务表加版本号 / 状态字段），但发现有两个弊端：

- 高并发下，乐观锁的 “版本冲突重试” 会导致大量无效请求，性能开销大；
- 数据库本身成了 “分布式锁的单点”，如果数据库压力大、响应慢，会拖慢整个任务调度的效率。

所以我们换成了**基于 Redisson 的 Redis 分布式锁**方案，具体逻辑是这样的：

1. **加锁逻辑**：当任意一个服务实例要执行 “课程过期提醒” 任务时，先通过 Redisson 尝试获取一把**分布式锁**（锁的 key 可以设计为 `task:course:expire:remind`，确保全局唯一）。Redisson 会利用 Redis 的 `SETNX`（或 Lua 脚本）实现 “原子性加锁”，同时还能设置**锁的过期时间**（避免服务宕机导致锁无法释放）和**看门狗机制**（自动续期，防止任务执行时间长于锁过期时间）。
2. **任务执行**：只有成功获取锁的实例，才会执行 “扫描待提醒课程、发送提醒通知” 的核心逻辑；其他实例获取锁失败后，会直接跳过本次调度，避免重复执行。
3. **释放锁**：任务执行完成后，通过 Redisson 自动释放锁（也能避免手动释放时的 “误删别人的锁” 问题，因为 Redisson 会验证锁的归属）。

这个方案带来的效果很明显：

- **可靠性**：任务重复执行率从原来的 30%+ 降到了几乎 0，用户不会再收到重复提醒；
- **性能**：因为把 “锁竞争” 的压力从数据库转移到了 Redis，任务调度的整体耗时降低了 40% 左右；
- **扩展性**：后续服务实例扩容时，分布式锁也能天然支持多实例的协调，不需要额外修改逻辑。

当然，用 Redis 分布式锁也得注意一些细节，比如**锁的粒度要合理**（我们是按 “整个任务” 加锁，如果任务可以拆分，也能做更细粒度的锁）、**要考虑 Redis 集群的高可用**（当时我们用了 Redis 主从 + 哨兵，保证锁服务不宕机）。



1. 我们在 XXL-Job 的 Admin 平台，配置了「课程过期提醒」的定时任务，Cron 表达式设为 `0 0 2 * * ?`（每天凌晨 2 点执行）。调度中心会按时触发任务，分发给注册的执行器（Executor）节点。”
2. **执行器的业务逻辑**：“执行器接收到任务后，会查询「未来 3 天内到期且用户未完成学习」的课程，再通过邮件、短信给用户发提醒。这里用到了 XXL-Job 的**任务参数传递**和**分片广播**能力（如果课程数据量大，还能把任务分片，让多台执行器并行处理不同批次的课程，提升效率）。”
3. **高并发与可靠性保障**：
   - 「分布式锁」：因为是多实例部署，用 XXL-Job 的**路由策略（如轮询、一致性 Hash）** 搭配「Redisson 分布式锁」，避免多实例重复执行任务。
   - 「失败重试与告警」：XXL-Job 支持**任务失败自动重试**（我们配置了 3 次重试），且失败后会通过邮件告警给开发人员，能及时发现并修复问题（比如下游服务超时导致的任务失败）。

# 课程发布的事务控制：通过本地消息表+异步任务调度，事务内持久化课程发布状态与同步任务，解耦多存储（Redis/ES/MinIO）数据同步，保障分布式环境下最终一致性

### 什么是分布式事务？

***首先理解什么是本地事务？***

平常我们在程序中通过spring去控制事务是利用数据库本身的事务特性来实现的，因此叫数据库事务，由于应用主要靠关系数据库来控制事务，此数据库只属于该应用，所以基于本应用自己的关系型数据库的事务又被称为本地事务。 

本地事务具有ACID四大特性，数据库事务在实现时会将一次事务涉及的所有操作全部纳入到一个不可分割的执行单元，该执行单元中的所有操作 要么都成功，要么都失败，只要其中任一操作执行失败，都将导致整个事务的回滚。 

***理解了本地事务，什么是分布式事务？***

现在的需求是课程发布操作后将数据写入数据库、redis、elasticsearch、MinIO四个地方，这四个地方已经不限制在一个数据库内，是由四个分散的服务去提供，与这四个服务去通信需要网络通信，而网络存在不可到达性，这种分布式系统环境下，通过与不同的服务进行网络通信去完成事务称之为**分布式事务。**

在分布式系统中分布式事务的场景很多：

例如用户注册送积分，银行转账，创建订单减库存，这些都是分布式事务。

### 控制分布式事务首先需要理解CAP理论，什么是CAP理论？

CAP是 Consistency、Availability、Partition tolerance三个词语的缩写，分别表示一致性、可用性、分区容忍性。

客户端经过网关访问用户服务的两个结点

`一致性`是指用户不管访问哪一个结点拿到的数据都是最新的，比如查询小明的信息，不能出现在数据没有改变的情况下两次查询结果不一样。

`可用性`是指任何时候查询用户信息都可以查询到结果，但不保证查询到最新的数据。

`分区容忍性`也叫分区容错性，当系统采用分布式架构时由于网络通信异常导致请求中断、消息丢失，但系统依然对外提供服务。

CAP理论要强调的是在分布式系统中这三点不可能全部满足，由于是分布式系统就要满足分区容忍性，因为服务之间难免出现网络异常，不能因为局部网络异常导致整个系统不可用。要么保证CP,要么保证AP

---

### 学习了CAP理论该如何控制分布式事务呢？

学习了CAP理论我们知道进行分布式事务控制要在C和A中作出取舍，保证一致性就不要保证可用性，保证可用性就不要保证一致，首先你确认是要CP还是AP，具体要根据应用场景进行判断。

CP的场景：满足C舍弃A，**强调一致性**。

跨行转账：一次转账请求要等待双方银行系统都完成整个事务才算完成，只要其中一个失败另一方执行回滚操作。

开户操作：在业务系统开户同时要在运营商开户，任何一方开户失败该用户都不可使用，所以要满足CP。

AP的场景：满足A舍弃C，**强调可用性**。

订单退款，今日退款成功，明日账户到账，只要用户可以接受在一定时间内到账即可。

注册送积分，注册成功积分在24分到账。

支付短信通信，支付成功发短信，短信发送可以有延迟，甚至没有发送成功。

在实际应用中符合AP的场景较多，其实虽然AP舍弃C一致性，实际上最终数据还是达到了一致，也就满足了最终一致性，所以业界定义了BASE理论。

#### 什么是BASE理论？

BASE 是 Basically Available(基本可用)、Soft state(软状态)和 Eventually consistent (最终一致性)三个短语的缩写。

`基本可用`：当系统无法满足全部可用时保证核心服务可用即可，比如一个外卖系统，每到中午12点左右系统并发量很高，此时要保证下单流程涉及的服务可用，其它服务暂时不可用。

`软状态`：是指可以存在中间状态，比如：打印自己的社保统计情况，该操作不会立即出现结果，而是提示你打印中，请在XXX时间后查收。虽然出现了中间状态，但最终状态是正确的。

`最终一致性`：退款操作后没有及时到账，经过一定的时间后账户到账，舍弃强一致性，满足最终一致性。

**满足CP？**

如果要满足CP就表示课程发布操作后向数据库、redis、elasticsearch、MinIO写四份数据，只要有一份写失败其它的全部回滚。

课程发布操作后，先更新数据库中的课程发布状态，更新后向redis、elasticsearch、MinIO写课程信息，只要在一定时间内最终向redis、elasticsearch、MinIO写数据成功即可。

### **消息表通过阶段状态实现任务幂等性**

```java
create table mq_message
(
    id                 bigint auto_increment comment '消息id'
        primary key,
    message_type       varchar(32)              not null comment '消息类型代码: course_publish ,  media_test',
    business_key1      varchar(64)              null comment '关联业务信息',
    business_key2      varchar(255)             null comment '关联业务信息',
    business_key3      varchar(512)             null comment '关联业务信息',
    execute_num        int unsigned default '0' not null comment '通知次数',
    state              char         default '0' not null comment '处理状态，0:初始，1:成功',
    returnfailure_date datetime                 null comment '回复失败时间',
    returnsuccess_date datetime                 null comment '回复成功时间',
    returnfailure_msg  varchar(2048)            null comment '回复失败内容',
    execute_date       datetime                 null comment '最近通知时间',
    stage_state1       char         default '0' not null comment '阶段1处理状态, 0:初始，1:成功',
    stage_state2       char         default '0' not null comment '阶段2处理状态, 0:初始，1:成功',
    stage_state3       char         default '0' not null comment '阶段3处理状态, 0:初始，1:成功',
    stage_state4       char         default '0' not null comment '阶段4处理状态, 0:初始，1:成功'
)
```

表通过 **阶段状态字段**（`stage_state1` 到 `stage_state4`）记录每个子任务的执行状态，从而保证任务的幂等性。

每完成一个阶段在相应的阶段状态字段打上完成标记，即使这个大任务没有完成再重新执行时，如果小阶段任务完成了也不会重复执行某个小阶段的任务。

### 熔断降级处理？

微服务中难免存在服务之间的远程调用，比如：内容管理服务远程调用媒资服务的上传文件接口，当微服务运行不正常会导致无法正常调用微服务，此时会出现异常，如果这种异常不去处理可能导致雪崩效应。

微服务的雪崩效应表现在服务与服务之间调用，当其中一个服务无法提供服务可能导致其它服务也死掉。

***如何解决由于微服务异常引起的雪崩效应呢？***

可以采用熔断、降级的方法去解决。

熔断降级的相同点都是为了解决微服务系统崩溃的问题，但它们是两个不同的技术手段，两者又存在联系。

**熔断：**

当下游服务异常而断开与上游服务的交互，它就相当于保险丝，下游服务异常触发了熔断，从而保证上游服务不受影响。

<img src="https://cdn.jsdelivr.net/gh/KNeegcyao/picdemo/img/image-20250828104923529.png" alt="image-20250828104923529" style="zoom:33%;" />

**降级：**

当下游服务异常触发熔断后，上游服务就不再去调用异常的微服务而是执行了降级处理逻辑，这个降级处理逻辑可以是本地一个单独的方法。

<img src="https://cdn.jsdelivr.net/gh/KNeegcyao/picdemo/img/image-20250828105004716.png" alt="image-20250828105004716" style="zoom:33%;" />

两者都是为了保护系统，熔断是当下游服务异常时一种保护系统的手段，降级是熔断后上游服务处理熔断的方法。

***具体实现：***

项目使用Hystrix框架实现熔断、降级处理，在feign-dev.yaml中配置。

1、开启Feign熔断保护

```YAML
feign:
  hystrix:
    enabled: true
  circuitbreaker:
    enabled: true
```

2、设置熔断的超时时间，为了防止一次处理时间较长触发熔断这里还需要设置请求和连接的超时时间，如下：

```Bash
hystrix:
  command:
    default:
      execution:
        isolation:
          thread:
            timeoutInMilliseconds: 30000  #熔断超时时间
ribbon:
  ConnectTimeout: 60000 #连接超时时间
  ReadTimeout: 60000 #读超时时间
  MaxAutoRetries: 0 #重试次数
  MaxAutoRetriesNextServer: 1 #切换实例的重试次数
```

3、定义降级逻辑

在`FeignClient`中指定`fallbackFactory` ，如下：

```Java
@FeignClient(value = "media-api",configuration = MultipartSupportConfig.class,fallbackFactory = MediaServiceClientFallbackFactory.class)
```

定义`MediaServiceClientFallbackFactory`如下：

```Java
@Slf4j
@Component
public class MediaServiceClientFallbackFactory implements FallbackFactory<MediaServiceClient> {
    @Override
    public MediaServiceClient create(Throwable throwable) {
        return new MediaServiceClient(){
            @Override
            public String uploadFile(MultipartFile upload, String objectName) {
                //降级方法
                log.debug("调用媒资管理服务上传文件时发生熔断，异常信息:{}",throwable.toString(),throwable);
                return null;
            }
        };
    }
}
```

**降级处理逻辑：**

返回一个null对象，上游服务请求接口得到一个null说明执行了降级处理。

### 你们数据量很大吗？为啥使用Elasticsearch？

主要是考虑我们要实现全文检索的效果所以使用Elasticsearch，全文检索的方式去搜索数据性能很高，它基于倒排索引表。正排索引是从文章中找词，倒排索引是根据词找文章，性能高。词是在索引库存储的。输入一个关键字从索引库中找词，找到词之后就找到了文章，整体性能高。

我们网站的数据量不大，项目架构时架构师决定使用Elasticsearch。

### 怎么使用Elasticsearch开发搜索模块？

1）首先创建索引（相当于mysql的表），将课程信息添加到索引库，对课程信息进行分词，存储到索引库。

2）开发一个搜索服务，编写一个搜索接口，调用Elasticsearch的api根据关键字搜索。

### 如何保证索引同步？

我们项目是使用本地任务表加xxl-job任务调度进行索引同步，具体的作法如下：

1）添加或修改或删除课程的同时向任务表插入一条记录，这条记录就记录了是添加还是修改还是删除了哪个课程。

2）任务调度定时扫描任务表，根据任务表的内容对课程信息进行同步，如果添加了课程将课程添加到索引库，如果修改了课程就修改索引库的课程，如果是删除了课程将课程信息从索引库删除。

如果对于实时要求很高的场景可以使用Canal将MySQL的数据同步到索引 。

实时不高可以使用任务调度、Logstash、消息队列的方式。

详细如下：

MQ：向mysql写数据的时候向mq写入消息，搜索服务监听MQ，收到消息后写入索引。使用MQ的优势是代码解耦，但是需要处理消息可靠性的问题有一定的技术成本，做到消息可靠性需要做到生产者投递成功、消息持久化以及消费者消费成功三个方面，另外还要做好消息幂等性问题。

Logstash： 开源实时日志分析平台 ELK包括Elasticsearch、Kibana、Logstash，Logstash负责收集、解析和转换日志信息，可以实现MySQL与Elasticsearch之间的数据同步。也可以实现解耦合并且是官方推荐，但需要增加学习与维护成本。

任务调度：向mysql写数据的时候记录修改记录，开启一个定时任务根据修改记录将数据同步到Elasticsearch。

### 什么是倒排索引？

我们传统的检索方式是通过遍历整篇文章，逐个比对找到对应的关键词位置，

而倒排索引是通过分词策略，形成词和文章的关系映射表，这种*词典+映射表的方式就是倒排索引*，有点类似于我们以前使用的新华字典。倒排索引可极大的提高查询效率

- 将每一个文档的数据利用**分词算法**根据语义拆分，得到一个个词条
- 创建表，每行数据包括词条、词条所在文档id、位置等信息
- 因为词条唯一性，可以给词条创建**正向**索引

此时形成的这张以词条为索引的表，就是倒排索引表，两者对比如下：

**正向索引**

| 3              | 华为小米充电器 | 49        |
| 4              | 小米手环       | 49        |
| ...            | ...            | ...       |

**倒排索引**

| **词条（索引）** | **文档id** |

### 相比正向索引，倒排索引有什么好处？

**正向索引**：

- 优点： 
  - 可以给多个字段创建索引
  - 根据索引字段搜索、排序速度非常快
- 缺点： 
  - 根据非索引字段，或者索引字段中的部分词条查找时，只能全表扫描。

**倒排索引**：

- 优点： 
  - 根据词条搜索、模糊搜索时，速度非常快
- 缺点： 
  - 只能给词条创建索引，而不是字段
  - 无法根据字段做排序

### mysql与elasticsearch的概念做一下对比?

| **MySQL** | **Elasticsearch** | **说明**                                                     |
| :-------- | :---------------- | :----------------------------------------------------------- |
| Table     | Index             | 索引(index)，就是文档的集合，类似数据库的表(table)           |
| Row       | Document          | 文档（Document），就是一条条的数据，类似数据库中的行（Row），文档都是JSON格式 |
| Column    | Field             | 字段（Field），就是JSON文档中的字段，类似数据库中的列（Column） |
| Schema    | Mapping           | Mapping（映射）是索引中文档的约束，例如字段类型约束。类似数据库的表结构（Schema） |
| SQL       | DSL               | DSL是elasticsearch提供的JSON风格的请求语句，用来操作elasticsearch，实现CRUD |

### “你说搜索延迟从2000ms降到50ms，这个测试是在什么环境下做的？怎么测的？”

测试环境是**学校实验室的服务器**（不是生产环境），数据用的是**课程数据库的测试数据集**（从学校教务系统导出的脱敏数据，共500条课程记录）。
 **测试方法很简单**：

- 用 **Python脚本**（`requests`库）模拟10次搜索请求，记录每次的响应时间。
- 优化前：平均延迟 **2000ms**（测试了10次，取中位数）。
- 优化后：用了IK分词+`multi_match`，同样10次测试，平均 **50ms**。
  **数据记录**：所有测试结果都写在项目文档里了（在GitHub仓库的`/test_results/`目录下，有CSV文件和截图）。我们小组一起复测过，结果一致。”

### “搜索转化率提升15%？你们怎么测的？学校项目哪来的转化率？”

在实验室项目里，**没有真实用户数据**，所以转化率是**模拟测试**的。

"搜索转化率提升15%"，是指在**课程搜索功能优化后**，用户完成特定目标行为（如"点击课程"或"查看课程详情"）的比例比优化前提高了15%。

 **具体做法**：

- 我们让5个同学（项目组成员）模拟用户行为：
  - 先用旧版搜索（2000ms延迟）搜索10次课程，记录他们点击了哪些课程（模拟‘转化’）
  - 再用新版搜索（50ms延迟）重复10次，记录点击数
- 旧版平均点击率：**35%**（35/100次）
- 新版平均点击率：**50%**（50/100次）
- **提升15%**（50%-35%=15%）
  **数据记录**：测试过程拍了视频，结果表存进了项目文档（GitHub的`/simulation/`目录）。我们组里所有人都确认过这个数据。”
